# Security Policy

## Reporting a vulnerability

Email allanianirudh05@gmail.com with a description of the issue and steps to reproduce it. You will get a reply within 7 days. Do not open a public issue for a suspected vulnerability.

## Scope and honest limitations

Ledgerline is a trust boundary, so its own limits are stated plainly. The design threat model is in `docs/VISION.md` section 4. The current honest limitations:

- The hash chain is unsigned SHA-256. There is no signing key in the current build. Anyone who can write the ledger store can recompute the whole chain and produce a valid one. Tamper evidence holds against edits that do not recompute the chain, and for bundles checked against a chain head the reviewer obtained separately. Signing and external anchoring are Phase 2 design, not shipped.
- Offline bundles prove self-consistency (the chain is intact), not authenticity (who wrote it).
- The control plane is open by default. With no `--api-token` and no per-approver tokens, anyone who can reach the gateway port can read session events (tool arguments included), export bundles, and decide approvals. The gateway logs a warning at startup in that case. Set a token before exposing the port beyond loopback. The proxy path itself is never authenticated by design: anyone who can reach the port can send tool calls through to the upstream MCP server.
- Approvals exist and are enforced in path (CLI and web page). With a per-approver token, the recorded approver name is bound to the credential. With only a shared token, or none, the recorded name is the one the caller supplies: a claim, not a proof.
- Redaction covers brokered secrets only. With a broker configured, the gateway injects upstream credentials per request (values from the environment, never the config file), denies a request carrying a brokered header with a foreign value, denies a tool call whose arguments contain a brokered secret before it is witnessed (so the secret never reaches the ledger), and redacts brokered values from upstream responses (JSON and SSE, line by line). A brokered value shorter than 8 characters refuses to start, because substring scans on short values would false-positive. The broker cannot revoke knowledge the agent already has from elsewhere (a matching value is indistinguishable from the broker's own), it does not scan non-tool traffic arguments, and it does not redact PTY output. Anything else the agent puts in arguments, and all terminal output, is stored exactly as sent. Treat the ledger file and every exported bundle as secret-bearing.
- Capture records each tool call and its policy outcome. It does not record the upstream result or the call duration, except keyed calls: their post-redaction responses are journaled up to 1 MiB for replay, and larger responses complete without a replay copy.
- Durable execution covers keyed tool calls only (X-Ledgerline-Idempotency-Key, scoped per session, bound to one tool and one arguments hash). A replay returns the recorded response without an upstream call and bypasses current policy by design, but never bypasses containment, which is checked first. A concurrent retry gets an in-flight error; a held retry gets the same approval id; an unknown outcome (crash mid-flight, or upstream failure without a response) is refused until a human resolves it as executed or not-executed. A resolved-executed key never re-forwards, even if the resolution was wrong. Journal rows live 24 hours, up to 1000 records, and are durable only with a SQLite ledger; in-memory mode loses them on restart. Journal rows are not hash-chained; only the unknown and resolved transitions are witnessed in the chain.
- Containment freezes a session inside a running gateway: the triggering call is denied, new calls from the session are denied, in-flight requests for it are cut off at the gateway, and pending held calls from it are denied. It is not a kill switch that survives a gateway restart, and it does not stop an agent process running outside the gateway (for example, a PTY session started by `ledgerline run`). A contained session unfreezes if the gateway restarts. Aborting an in-flight request does not undo a side effect the upstream already executed. Containment is keyed on the ledger session header and on the upstream MCP sessions observed on it: rotating the ledger header alone does not evade it, but starting a fresh upstream MCP session does, because the proxy path is unauthenticated by design. Clients that send no session header share the "default" session, so containing "default" blocks every headerless client.
- A proposal is never forwarded. The agent is told the action was NOT executed, and a human applying it out of band is the human's own act, outside the gateway's observation. The ledger records that a human claimed to apply it, not that the action happened. That claim is only as trustworthy as the control-plane token: with no token set, anyone who can reach the port can mark a proposal applied. Identical retries return the existing proposal id instead of queueing duplicates; the queue holds 1000 proposals and entries expire after 24 hours.
- Upstream pinning covers the configured upstream URL only (SHA-256 of the normalized URL, stored in the pin file). It proves the configured upstream string matches the pin file, nothing more: it does not verify what the upstream server is, the pin file itself is unprotected against a process running as the same OS user, the first run trusts whatever upstream was passed, and a re-approval is only as trustworthy as the operator who passed `--reapprove-upstream`. Displayed copies of the upstream URL (logs, errors, `/v1/upstream`) have credentials stripped; the URL itself is still used verbatim for the actual request.

If you find a gap between what the docs promise and what the code does, that is a security issue. Report it.
