# Security Policy

## Reporting a vulnerability

Email allanianirudh05@gmail.com with a description of the issue and steps to reproduce it. You will get a reply within 7 days. Do not open a public issue for a suspected vulnerability.

## Scope and honest limitations

Ledgerline is a trust boundary, so its own limits are stated plainly. The design threat model is in `docs/VISION.md` section 4. The current honest limitations:

- The hash chain is unsigned SHA-256. There is no signing key in the current build. Anyone who can write the ledger store can recompute the whole chain and produce a valid one. Tamper evidence holds against edits that do not recompute the chain. It also holds for bundles checked against a chain head the reviewer obtained separately. Signing and external anchoring are Phase 2 design, not shipped.
- Offline bundles prove self-consistency (the chain is intact), not authenticity (who wrote it).
- The control plane is open by default. With no `--api-token` and no per-approver tokens, anyone who can reach the gateway port can read session events. This includes tool arguments. Such a person can also export bundles and decide approvals. The gateway logs a warning at startup in that case. Set a token before you expose the port beyond loopback. The proxy path itself has no authentication by design. Anyone who can reach the port can send tool calls through to the upstream MCP server.
- Approvals exist. They are enforced in path, in the CLI and on the web page. With a per-approver token, the recorded approver name is bound to the credential. With only a shared token, or none, the recorded name is the one the caller supplies. It is a claim, not a proof.
- Redaction covers brokered secrets only. With a broker configured, the gateway injects upstream credentials per request. Values come from the environment, never the config file. The gateway denies a request that carries a brokered header with a foreign value. It denies a tool call whose arguments contain a brokered secret before it is witnessed, so the secret never reaches the ledger. It redacts brokered values from upstream responses, JSON and SSE, line by line. A brokered value shorter than 8 characters refuses to start, because substring scans on short values would false-positive. The broker cannot revoke knowledge the agent already has from elsewhere. A matching value is indistinguishable from the broker's own. The broker does not scan non-tool traffic arguments. It does not redact PTY output. Anything else the agent puts in arguments is stored exactly as sent. All terminal output is stored exactly as sent. Treat the ledger file and every exported bundle as secret-bearing.
- Capture records each tool call and its policy outcome. It does not record the upstream result or the call duration. Keyed calls are the exception. Their post-redaction responses go into the journal up to 1 MiB for replay. Larger responses complete without a replay copy.
- Durable execution covers keyed tool calls only (X-Ledgerline-Idempotency-Key, scoped per session, bound to one tool and one arguments hash). A replay returns the recorded response without an upstream call. A replay bypasses current policy by design. A replay never bypasses containment. Containment is checked first. A concurrent retry gets an in-flight error. A held retry gets the same approval id. An unknown outcome is refused until a human resolves it as executed or not-executed. An unknown outcome means a crash mid-flight, or an upstream failure without a response. A resolved-executed key never re-forwards, even if the resolution was wrong. Journal rows live 24 hours, up to 1000 records. Journal rows are durable only with a SQLite ledger. In-memory mode loses them on restart. Journal rows are not hash-chained. Only the unknown and resolved transitions go into the chain.
- Tools-drift detection trusts the first tool surface it can read as the baseline. The surface comes from the startup probe. If the probe finds nothing, it comes from the first tools/list passing through. The baseline is stored in the ledger store, so restarts do not reset it. From then on, a tools/call for a name outside the baseline is denied until a human accepts the new surface. The human accepts with --reapprove-tools, or with POST /v1/tools/accept. Accept makes the next observed list the baseline, witnessed. Drift enforcement requires a control-plane token. With no --api-token and no per-approver tokens, POST /v1/tools/accept is open to anyone who can reach the port. This includes the agent itself. A compromised agent can re-anchor trust in three requests. The gateway logs a warning at startup in that case. The first sighting is trusted. A server already compromised before the first gateway start baselines its malicious tools. The pin's first-run trust problem applies here too. Enforcement covers unknown names only. Removals and description/schema changes go into the ledger as drift. They do not block baseline tools. The probe follows tools/list pagination cursors to build the full baseline. A partial page passing through is ignored for baseline purposes. It is never treated as a surface. A tools/list response that does not parse changes nothing. This includes an undecodable SSE stream. With no baseline at all, calls stay allowed. In-memory mode loses the baseline on restart. The baseline row in the ledger store is not covered by chain verification. A DB writer can rewrite it while verify stays green. This sits within the already-conceded DB-write power. Session-scoped bundles exclude gateway-wide baseline and drift events. The full chain holds them.
- Containment freezes a session inside a running gateway. The triggering call is denied. New calls from the session are denied. In-flight requests for the session are cut off at the gateway. Pending held calls from the session are denied. Containment is not a kill switch that survives a gateway restart. It does not stop an agent process running outside the gateway. An example is a PTY session started by `ledgerline run`. A contained session unfreezes if the gateway restarts. Aborting an in-flight request does not undo a side effect the upstream already executed. Containment is keyed on the ledger session header. It is also keyed on the upstream MCP sessions observed on it. Rotating the ledger header alone does not evade it. Starting a fresh upstream MCP session does evade it, because the proxy path has no authentication by design. Clients that send no session header share the "default" session. Containing "default" blocks every headerless client.
- A proposal is never forwarded. The agent is told the action was NOT executed. A human applying it out of band is the human's own act, outside the gateway's observation. The ledger records that a human claimed to apply it, not that the action happened. That claim is only as trustworthy as the control-plane token. With no token set, anyone who can reach the port can mark a proposal applied. Identical retries return the existing proposal id instead of queueing duplicates. The queue holds 1000 proposals. Entries expire after 24 hours.
- Upstream pinning covers the configured upstream URL only (SHA-256 of the normalized URL, stored in the pin file). It proves the configured upstream string matches the pin file, nothing more. It does not verify what the upstream server is. The pin file itself has no protection against a process running as the same OS user. The first run trusts whatever upstream was passed. A re-approval is only as trustworthy as the operator who passed `--reapprove-upstream`. Displayed copies of the upstream URL have credentials stripped. This covers logs, errors, and `/v1/upstream`. The URL itself is still used verbatim for the actual request.
- The hook bridge checks a proposed native tool call. It does not see the tool result. It does not stop an agent process. If the harness does not run the hook, no check happens. An allow means Ledgerline does not object. It does not grant harness permission. A standalone hold blocks at once. It never waits for a human. A gateway hold waits only up to the bridge hold timeout plus 30 seconds of client grace. If the bridge stops waiting, the gateway hold is cancelled. A late approval after that records no allow. The agent must retry for a fresh hold. The standalone bridge scans arguments for brokered secrets only when --broker is set. Without --broker, it records arguments as sent, secrets included. Gateway mode always scans. Hook payloads above 10 MB block, on the bridge and on the endpoint. Drift detection does not apply to hook calls. The bridge ignores cwd, so policy authors must match absolute paths. No policy flags means allow-all. An empty policy file is refused. Fail-open also allows when the gateway ledger fails, and that allow has no record. The Gemini default is 25 seconds. The default Gemini wait is 55 seconds. That sits below the 60 second Gemini kill line. A tiny race remains. If the gateway records an allow and the bridge disconnects before the answer lands, the ledger holds an allow for a call the harness may block. The ledger cannot tell read_file from read_many_files. Both map to read.

If you find a gap between what the docs promise and what the code does, that is a security issue. Report it.
