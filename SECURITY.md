# Security Policy

## Reporting a vulnerability

Email allanianirudh05@gmail.com with a description of the issue and steps to reproduce it. You will get a reply within 7 days. Do not open a public issue for a suspected vulnerability.

## Scope and honest limitations

Ledgerline is a trust boundary, so its own limits are stated plainly. The design threat model is in `docs/VISION.md` section 4. The current honest limitations:

- The hash chain is unsigned SHA-256. There is no signing key in the current build. Anyone who can write the ledger store can recompute the whole chain and produce a valid one. Tamper evidence holds against edits that do not recompute the chain. It also holds for bundles checked against a chain head the reviewer obtained separately. Signing and external anchoring are Phase 2 design, not shipped.
- Offline bundles prove self-consistency (the chain is intact), not authenticity (who wrote it).
- The control plane is open by default. With no `--api-token` and no per-approver tokens, anyone who can reach the gateway port can read session events. This includes tool arguments. Such a person can also export bundles and decide approvals. The gateway logs a warning at startup in that case. Set a token before you expose the port beyond loopback. The proxy path has no authentication unless --require-agent-token is set. Without it, anyone who can reach the port can send tool calls through to the upstream MCP server.
- Approvals exist. They are enforced in path, in the CLI and on the web page. With a per-approver token, the recorded approver name is bound to the credential. With only a shared token, or none, the recorded name is the one the caller supplies. It is a claim, not a proof.
- Redaction covers brokered secrets only. With a broker configured, the gateway injects upstream credentials per request. Values come from the environment, never the config file. The gateway denies a request that carries a brokered header with a foreign value. It denies a tool call whose arguments contain a brokered secret before it is witnessed, so the secret never reaches the ledger. It redacts brokered values from upstream responses, JSON and SSE, line by line. A brokered value shorter than 8 characters refuses to start, because substring scans on short values would false-positive. The broker cannot revoke knowledge the agent already has from elsewhere. A matching value is indistinguishable from the broker's own. The broker does not scan non-tool traffic arguments. It does not redact PTY output. Anything else the agent puts in arguments is stored exactly as sent. All terminal output is stored exactly as sent. Treat the ledger file and every exported bundle as secret-bearing.
- Capture records each tool call and its policy outcome. It does not record the upstream result or the call duration. Keyed calls are the exception. Their post-redaction responses go into the journal up to 1 MiB for replay. Larger responses complete without a replay copy.
- Durable execution covers keyed tool calls only (X-Ledgerline-Idempotency-Key, scoped per session, bound to one tool and one arguments hash). A replay returns the recorded response without an upstream call. A replay bypasses current policy by design. A replay never bypasses containment. Containment is checked first. A concurrent retry gets an in-flight error. A held retry gets the same approval id. An unknown outcome is refused until a human resolves it as executed or not-executed. An unknown outcome means a crash mid-flight, or an upstream failure without a response. A resolved-executed key never re-forwards, even if the resolution was wrong. Journal rows live 24 hours, up to 1000 records. Journal rows are durable only with a SQLite ledger. In-memory mode loses them on restart. Journal rows are not hash-chained. Only the unknown and resolved transitions go into the chain.
- Tools-drift detection trusts the first tool surface it can read as the baseline. The surface comes from the startup probe. If the probe finds nothing, it comes from the first tools/list passing through. The baseline is stored in the ledger store, so restarts do not reset it. From then on, a tools/call for a name outside the baseline is denied until a human accepts the new surface. In detect mode the denial is observed instead: the ledger records a policy_decision with deny and mode detect, then a tool_call with decision allow, sharing one decision id, and the call runs. The human accepts with --reapprove-tools, or with POST /v1/tools/accept. Accept makes the next observed list the baseline, witnessed. Drift enforcement requires a control-plane token. With no --api-token and no per-approver tokens, POST /v1/tools/accept is open to anyone who can reach the port. This includes the agent itself. A compromised agent can re-anchor trust in three requests. The gateway logs a warning at startup in that case. The first sighting is trusted. A server already compromised before the first gateway start baselines its malicious tools. The pin's first-run trust problem applies here too. Enforcement covers unknown names only. Removals and description/schema changes go into the ledger as drift. They do not block baseline tools. The probe follows tools/list pagination cursors to build the full baseline. A partial page passing through is ignored for baseline purposes. It is never treated as a surface. A tools/list response that does not parse changes nothing. This includes an undecodable SSE stream. With no baseline at all, calls stay allowed. In-memory mode loses the baseline on restart. The baseline row in the ledger store is not covered by chain verification. A DB writer can rewrite it while verify stays green. This sits within the already-conceded DB-write power. Session-scoped bundles exclude gateway-wide baseline and drift events. The full chain holds them. The gateway checks the drift gate twice: once at arrival, and again when it forwards. A baseline change between the two checks denies the call in prevent mode even when the arrival check allowed it. The ledger then holds a policy_decision allow from arrival and a tools_drift deny under one decision id, with no tool_call. A policy_decision allow is the rule evaluation at arrival. It is not proof the call ran. Only a tool_call event records that the call passed the last gate and was sent to run. The record has two limits. An upstream error after the witness leaves a tool_call with no upstream execution. The hook path never observes execution. The allow carries no preempted mark in that case. A held call is different. Its hold genuinely parked the call, so a later drift denial does not preempt its decision.
- Containment freezes a session inside a running gateway. The triggering call is denied. New calls from the session are denied. In-flight requests for the session are cut off at the gateway. Pending held calls from the session are denied. Containment is not a kill switch that survives a gateway restart. It does not stop an agent process running outside the gateway. An example is a PTY session started by `ledgerline run`. A contained session unfreezes if the gateway restarts. Aborting an in-flight request does not undo a side effect the upstream already executed. Containment is keyed on the ledger session header. It is also keyed on the upstream MCP sessions observed on it. Rotating the ledger header alone does not evade it. Starting a fresh upstream MCP session does evade it, because without proxy-path agent tokens a new MCP session is a new identity. With tokens on, the agent id is bound to the token. Clients that send no session header share the "default" session. Containing "default" blocks every headerless client.
- A proposal is never forwarded. The agent is told the action was NOT executed. A human applying it out of band is the human's own act, outside the gateway's observation. The ledger records that a human claimed to apply it, not that the action happened. That claim is only as trustworthy as the control-plane token. With no token set, anyone who can reach the port can mark a proposal applied. Identical retries return the existing proposal id instead of queueing duplicates. The queue holds 1000 proposals. Entries expire after 24 hours.
- Detection mode observes instead of enforcing. A rule with mode detect lets the call run. The ledger records the would-be decision and the tool_call sent to run. Both share one decision id. A detected proposal is never queued. A human must never apply a call that was already sent to run. A detected hold asks no human. A detected contain freezes nothing. A rule with no mode means prevent. New rules start in detect mode. The detect promise covers policy rules only. A batch, a brokered secret, and a foreign brokered header are boundary refusals. They deny in detect mode too.
- Ledger events carry mode, decision id, policy hash, agent id, and preempted_by (schema v4). The hash covers them with the rest of the event. Old v1, v2, and v3 chains still verify. A database from an older build migrates on open. The policy hash is the SHA-256 of the policy file. It says which policy version made a past decision. A mode flip changes the hash. The hash then covers the file bytes plus the canonical mode overrides. The agent id is set when --require-agent-token is on. It stays empty without it. Rows are then labelled by session id, not by agent. Detection mode doubles the events per matched call: one policy_decision plus one tool_call. A policy_decision allow is the rule evaluation at arrival. It is not proof the call ran. Only a tool_call event records that the call passed the last gate and was sent to run.
- The dashboard pulls from peer gateways on demand. The peers file holds one control-plane token per peer. Treat it like a secret. The gateway refuses to start when the file is group- or world-readable. Each peer token is sent to that peer as its control-plane token. A leaked peer token lets its holder read that peer ledger. It also lets the holder decide that peer approvals. The gateway verifies each peer chain itself. It pulls the full peer chain and runs the local chain check on it. It never trusts the peer own /v1/verify answer. A peer chain over 5000 events is too large to pull and verify, so it shows chain_ok false with the total. A peer whose chain fails the local check shows chain_ok false with the failure text. Local verification proves the chain is intact as presented, not who wrote it. The chain is unsigned, so a peer that recomputes a whole chain can still present a valid one. The dashboard shows a peer that does not answer as down. It never hides it. The merged timeline sorts by timestamp across gateways. It is not one chain order. Clocks must agree, or the merged order lies. Each peer pull in a merged timeline caps at 500 events. A peer with more filtered events contributes its newest 500 rows. The merged answer names capped peers in truncated and gives each peer filtered total in peer_totals. Each peer pull asks for that peer own events only, so a peer never returns another peer events under its name, and mutual peers cannot recurse. A pull that reaches a peer already visited is refused. Peer response bodies cap at 8 MB. A larger answer is refused. Peer urls must use https, except loopback hosts (localhost, 127.0.0.1, ::1), which may use http. A plain http url to any other host is refused when the peers file loads, so the control-plane token never crosses a plain http link to a remote host.
- A policy mode flip is a policy change. It is witnessed in the ledger as a policy_change event. With a per-approver token, the recorded actor name is bound to the credential. A flip with only the shared control token is refused: it carries no credential for its actor. With no approver token configured, the flip is recorded as "unattributed" instead of trusting the body value. A flip from prevent to detect opens the rule at once. A flip from detect to prevent blocks work at once. The flip persists in the modes file next to the policy file. A process that can write the modes file can change enforcement at the next gateway start. The file has no protection against a process running as the same OS user. This sits within the already-conceded DB-write power. A gateway that runs on static deny and hold lists refuses flips.
- Agent identity tokens are opt-in HMAC-SHA256 tokens. The gateway mints them with `ledgerline token issue`. Each token names one agent id and one owner. The default life is 8 hours. The max is 7 days. The gateway checks the token on every proxy-path request. A missing, invalid, expired, or revoked token gets HTTP 401 with a JSON-RPC error body. The rejection is not witnessed in the ledger. It is logged to stderr. The gateway never forwards the agent token upstream. It also strips Authorization and X-Ledgerline-Token from upstream requests. Revocation persists in ledgerline-revoked-tokens.json and survives a gateway restart. The key file holds one hex or base64 key. Treat it like a secret. A leaked key lets anyone mint tokens as any agent. The token proves identity to this gateway only. It is not OAuth and it carries no scope. The idempotency journal stays keyed by session header. Two agents that share one session header share its idempotency namespace. A token may carry an aud claim. The audience is the gateway upstream URL. A token with an audience works only on a gateway that fronts that upstream. The audience is the upstream URL exactly as configured. Spell it the same way on every restart. A different spelling breaks all audience-bound tokens. --token-audience sets a fixed audience instead of the upstream URL. --token-strict-audience refuses tokens with no audience. Turn strict mode on only after every client holds an audience-bound token. A token with no audience is a legacy token. It works on any gateway until it expires, at most 7 days after minting. Two gateways that front the same upstream and share one key still accept each other's tokens. Separate keys give full isolation. The proxy path accepts the token as X-Ledgerline-Agent-Token or as Authorization: Bearer. A token issued more than 60 seconds in the future is refused. The expiry must sit after the issue time. Signature validation and the revocation check run under one lock, so a revoke cannot slip one request through. Revocation marks the token in memory first, then witnesses the event, then writes the file. A file failure leaves the revocation standing in memory, and the revoke response says the persistence failed. A restart then loses it. A ledger failure also leaves the revocation standing, and the revoke response is 500 and says the witness failed. The gateway logs a warning at startup when proxy-path agent auth is off.
- Upstream pinning covers the configured upstream URL only (SHA-256 of the normalized URL, stored in the pin file). It proves the configured upstream string matches the pin file, nothing more. It does not verify what the upstream server is. The pin file itself has no protection against a process running as the same OS user. The first run trusts whatever upstream was passed. A re-approval is only as trustworthy as the operator who passed `--reapprove-upstream`. Displayed copies of the upstream URL have credentials stripped. This covers logs, errors, and `/v1/upstream`. The URL itself is still used verbatim for the actual request.
- The hook bridge checks a proposed native tool call. It does not see the tool result. It does not stop an agent process. If the harness does not run the hook, no check happens. An allow means Ledgerline does not object. It does not grant harness permission. A standalone hold blocks at once. It never waits for a human. A gateway hold waits only up to the bridge hold timeout plus 30 seconds of client grace. If the bridge stops waiting, the gateway hold is cancelled. A late approval after that records no allow. The agent must retry for a fresh hold. The standalone bridge scans arguments for brokered secrets only when --broker is set. Without --broker, it records arguments as sent, secrets included. Gateway mode always scans. Hook payloads above 10 MB block, on the bridge and on the endpoint. Drift detection does not apply to hook calls. The bridge ignores cwd, so policy authors must match absolute paths. No policy flags means allow-all. An empty policy file is refused. Fail-open also allows when the gateway ledger fails, and that allow has no record. The Gemini default is 25 seconds. The default Gemini wait is 55 seconds. That sits below the 60 second Gemini kill line. A tiny race remains. If the gateway records an allow and the bridge disconnects before the answer lands, the ledger holds an allow for a call the harness may block. The ledger cannot tell read_file from read_many_files. Both map to read.

If you find a gap between what the docs promise and what the code does, that is a security issue. Report it.
